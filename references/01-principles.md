# 01 设计原则

> 主动不是定时器，是"愿望 → 许可 → 时机 → 出口"四层漏斗。

## 1. 为什么不能是定时器

固定间隔只能回答"到点了吗"，回答不了：

- 现在有没有值得说的事？
- 说了会不会打扰？
- 对方刚拒绝过，还要不要继续？
- 这是社交消息，还是系统告警？

把"到点"当成"该说"，短期看起来像主动，长期会退化成骚扰或机械推送。

## 2. 四层漏斗

```
感知 Perceive  → 愿望 Desire → 许可 Gate → 审议 Deliberate → 时机 Timing → 出口 Dispatch → 反馈 Feedback
```

| 层 | 回答 | 不通过时 |
| --- | --- | --- |
| 愿望 | 为什么说？ | 没有 evidence 就不生成 |
| 许可 | 该不该说？ | 丢弃并记原因（低置信、面子风险、静默、窗口、间隔、配额、评分） |
| 审议 | 说哪一件？ | 只留最高 BDI |
| 时机 | 现在合适吗？ | send / defer / skip |
| 出口 | 怎么落地？ | shadow / 预占 / 投递 / 失败释放 |
| 反馈 | 效果如何？ | decay/pace/shadow |

## 3. 三个不可混用的分界

### 3.1 社交消息 vs 系统/计划消息

`last_social_bot_at` 只记录**社交性发送**。

工具回执、余额告警、审批提醒、学习提醒都是 `system` / `scheduled`。把它们算成"机器人刚说过话"，社交主动会被永久饿死（X2）。

### 3.2 后台检查 vs 主动意图

后台检查（评论轮询、余额检查）不能写意图历史，也不能消耗时机预算（X3）。
本实现用 `observe_background()`：只写审计，不产生 intent，不调模型。

### 3.3 安静窗口 vs 系统告警

`quiet` 与 `active window` 只拦 `social` / `scheduled`；`system` 放行（X7）。
余额不足、待审批、长任务失败不该等到早上才报。

## 4. 十条反模式（出现任意一条即实现错误）

| ID | 反模式 | 后果 |
| --- | --- | --- |
| X1 | 用固定间隔代替漏斗 | 退化成定时任务 |
| X2 | 把工具/环境消息计入 `last_social_bot_at` | 社交永久饿死 |
| X3 | 让检查类消耗时机预算 | 半天预算耗尽，全天 fallback |
| X4 | 生成无依据的空闲分享 | 模型必然拒绝，浪费一次判定 |
| X5 | 注入 prompt 即标记"已问过" | 确认事项永远不会被再问 |
| X6 | 硬删记忆前不留快照 | 不可恢复（记忆系统的约束） |
| X7 | 用安静窗口拦系统告警 | 余额/审批/提醒失效 |
| X8 | 失败后静默重试 | 重复消息 + 配额错乱 |
| X9 | 阈值散落在代码里 | 无法调参、无法验收 |
| X10 | 多个调度器各自判断"要不要说话" | 行为不可复现 |

## 5. 默认安全姿势

- 首部署 `mode=shadow`：完整判定、生成内容、写审计，但不调用 `send_text`。
- 观察 24h 再 `enforce`；`mode off` 是立即停。
- 自动抽取/生成都必须有 evidence；无依据宁可不生成。
- 投递失败释放预占配额，写 `failed`，**不重试**（X8）。
- 单流部署，一个实例一条聊天流；多聊天多实例，避免预算/静默/账本串流。

## 6. 与规格的对应

本 skill 按《AI 主动行为部署规格 v1.0》的 R/G/T/E/F 规则 clean-room 实现；参考实现里的领域活动（学习提醒、唱歌、空间动态、B 站回复、审批中心、表情包模式）不在 v1 内。

三处显式取舍：

1. `S2` 的"min_confidence < score_threshold"被实现为**可产生候选的可行性检查**；默认值本身可行，但会给出 warning。
2. 开放话题 TTL 从 `max(now, due_at)` 起算，保证"下周"的承诺不会在创建 48h 后先过期；规格原文只写 TTL 48h。
3. D1/D7 在宿主未显式标记时做保守推断（30 分钟 / 24h 内 2 次拒绝或困惑），显式值永远优先。
